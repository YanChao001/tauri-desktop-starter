# 5. 保留 GitFlow 并从 main 回流发布历史

- 状态：已采纳
- 日期：2026-10-22
- 决策者：项目发起人
- 相关：[ADR 0002](./0002-git-merge-strategy.md)、[Git 协作规范](../conventions/git-workflow.md)

## 背景

此前同一 release 分支分别合入 `main` 和 `develop`，文件相同却留下不同的合并提交。下一轮发布时，`main` 的严格同步要求又迫使 release 补入一次不改变文件的历史合并。维护者选择继续使用 GitFlow，需要纠正发布回流，而非改写已合并历史或改为 GitHub Flow。

## 备选方案

| 方案                                      | 收益                        | 代价                                   |
| ----------------------------------------- | --------------------------- | -------------------------------------- |
| 继续分别合入两条长期分支                  | 沿用原操作                  | 未回流正式发布提交，可能重复补历史合并 |
| release 合入 main，再由 main 回流 develop | 保留 GitFlow 和正式发布祖先 | 两个 PR 需按顺序完成                   |
| 改为单主分支                              | 减少分支与发布步骤          | 改变维护者选定的协作模型               |

## 决策

采用第二种方案，继续使用 `develop`、`main`、短期分支和 PR `--no-ff` 合并。已合并提交和已有标签保持原样；发布与回流的具体操作统一由 Git 协作规范维护。

`main` 保留必需 CI，但关闭“来源分支必须最新”；`develop` 保持严格同步。CI 检查 PR 合并结果，发布者在合并前核对已验证的来源和目标 SHA，目标变化后重新验证。此规则长期应用，不为单次发布临时关闭门禁；禁止强推、PR、必需检查及管理员约束继续生效。

## 后果与恢复

正式发布提交进入 `develop` 后，后续 release 自然继承它。无需复制已合并的功能提交，也不需要为整洁移动历史标签。

宽松状态检查不能自动防止目标分支推进后的组合回归，因此发布合并串行执行并核对目标 SHA。出现并行发布冲突或漏检时，暂停下一次发布，重新验证合并结果；必要时恢复 `main` 严格同步设置，通过显式同步分支解决兼容问题，不删除用户数据或重写保护分支。

## 复查条件

需要并行维护多个正式版本、频繁交叉 hotfix，或无法保证发布基线核对时，重新评估同步规则及合并队列支持。
