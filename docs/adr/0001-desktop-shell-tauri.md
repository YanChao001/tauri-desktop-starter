# 1. 采用 Tauri 2 作为桌面外壳

- 状态：已采纳
- 日期：2026-10-19
- 决策者：项目发起人
- 相关：[架构说明](../architecture.md)

## 背景

需要开发一款跨平台桌面应用，硬性约束：

- 安装包要小，分发靠官网直接下载，用户对体积敏感
- 应用常驻后台，内存占用要低
- 界面要现代、交互丰富，团队以前端技术为主
- 需要访问本地文件与系统能力

备选方案从"打包体积 / 性能 / UI 表现力 / 团队成本"四个维度评估。

## 备选方案

| 方案                | 优点                                                                           | 缺点                                             |
| ------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------ |
| **Tauri 2 + React** | 安装包 1.4MB 级，内存低；UI 复用 Web 生态；Rust 提供系统能力；安全模型默认拒绝 | 依赖系统 WebView，三端渲染有差异；需要少量 Rust  |
| Electron + React    | 生态最成熟，渲染绝对一致，纯 JS                                                | 安装包 120MB+，空闲内存 300MB+，与体积目标冲突   |
| Flutter             | 自绘引擎，动效与视觉一致性强，可同时上移动端                                   | 包体 30MB+；桌面周边（打包、更新、托盘）依赖社区 |
| Avalonia + C#       | .NET 团队上手快，数据密集型界面成熟                                            | 团队无 .NET 积累；现代视觉需要额外投入           |
| Qt + QML            | 性能与体积均衡，工业场景验证充分                                               | 学习曲线陡；许可证合规成本                       |

## 决策

采用 **Tauri 2 + Rust + React 19 + TypeScript + Vite**，UI 基于 shadcn/ui 与 Tailwind 4。

## 后果

**正面**

- 实测安装包 NSIS 1.4MB / MSI 1.9MB，可执行文件 3.4MB，远低于其他方案
- 冷启动快，系统 WebView 通常已常驻内存
- UI 开发完全复用 Web 生态，组件、图表、动画都有现成方案
- capabilities 白名单让"前端被攻破"的爆炸半径可控
- 同一套代码后续可延伸到移动端

**负面**

- 三个平台三种 WebView 引擎，CSS/JS 行为需要分别验证；Linux 的 WebKitGTK 版本偏旧，复杂动画可能掉帧
- Windows 依赖 WebView2 运行时，极老旧的 Win10 机器需要引导安装
- 团队需要理解 Rust 的所有权与错误处理，虽然本项目中 Rust 只承担薄薄一层
- 生态相比 Electron 仍有差距，冷门系统能力可能需要自己写

**缓解措施**

- UI 在三端各做一次冒烟测试，写入发布检查清单
- Rust 侧只写命令，业务逻辑留在 TypeScript，降低语言门槛
- 复杂动效避免依赖 WebView 特性，必要时降级为 CSS transition

## 复查条件

出现以下任一情况时重新评估：

- 需要高频使用 WebGL / WebGPU，且系统 WebView 性能不达标
- Linux 成为一等目标平台，且 WebKitGTK 无法满足渲染要求
- 团队完全没有 Rust 能力，且无法补充
- 需要支持 Windows 7（WebView2 已不支持）
