# 1. 采用 Tauri 2 作为桌面外壳

- 状态：已采纳
- 日期：2026-10-19
- 决策者：项目发起人
- 相关：[架构说明](../architecture.md)

## 背景

需要开发一款跨平台桌面应用，硬性约束：

- 安装包要小，分发靠官网直接下载，用户对体积敏感
- 应用常驻后台，内存占用要低
- 界面要现代、交互丰富，团队以前端技术为主
- 需要访问本地文件与系统能力

备选方案从"打包体积 / 性能 / UI 表现力 / 团队成本"四个维度评估。

## 备选方案

| 方案                | 优点                                                                      | 缺点                                                   |
| ------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------ |
| **Tauri 2 + React** | 复用系统 WebView 与 Web UI 生态，Rust 提供系统能力；核心 / 插件权限可限定 | 依赖系统 WebView，平台渲染存在差异；需要维护 Rust 服务 |
| Electron + React    | 随包提供 Chromium / Node.js，Web 技术栈便于复用                           | 随包运行时增加分发与资源成本，需按真实应用测量         |
| Flutter             | 自绘界面，可评估跨桌面与移动端复用                                        | 需维护 Dart 技术栈并核对所需桌面插件能力               |
| Avalonia + C#       | .NET 团队上手快，数据密集型界面成熟                                       | 团队无 .NET 积累；现代视觉需要额外投入                 |
| Qt + QML            | 性能与体积均衡，工业场景验证充分                                          | 学习曲线陡；许可证合规成本                             |

## 决策

采用 **Tauri 2 + Rust + React 19 + TypeScript + Vite**，UI 基于 shadcn/ui 与 Tailwind 4。

## 后果

**正面**

- 复用系统 WebView，避免另行随包分发整套浏览器运行时；实际包体与启动性能按发布构建测量
- UI 开发完全复用 Web 生态，组件、图表、动画都有现成方案
- 核心与插件权限可以通过 capabilities 限定；自定义命令仍需单独设计 ACL 与入参边界
- 可评估后续平台扩展，当前工程只配置桌面端

**负面**

- Windows 使用 WebView2，macOS 使用 WKWebView，Linux 使用 WebKitGTK；实现、版本和系统集成不同，CSS / JS 与窗口行为需分别验证
- Windows 依赖 WebView2 运行时，目标机器缺失时需要准备安装方案
- 团队需要维护 Rust 的所有权、错误处理、持久化与系统集成
- 生态相比 Electron 仍有差距，冷门系统能力可能需要自己写

**缓解措施**

- UI 在三端各做一次冒烟测试，写入发布检查清单
- 命令层只做边界适配，设置、数据库、更新和系统能力留在对应 Rust 服务；界面状态与交互留在 TypeScript
- 复杂动效避免依赖 WebView 特性，必要时降级为 CSS transition

## 复查条件

出现以下任一情况时重新评估：

- 需要高频使用 WebGL / WebGPU，且系统 WebView 性能不达标
- 目标 Linux 环境的 WebKitGTK 无法满足渲染要求
- 团队完全没有 Rust 能力，且无法补充
- 需要支持超出当前工具链或 WebView 兼容范围的系统
