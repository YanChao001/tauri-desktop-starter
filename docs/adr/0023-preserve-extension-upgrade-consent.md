# 23. 对授权范围未变的可信升级复用现有授权

- 状态：已采纳
- 日期：2026-10-29
- 局部取代：[0011](./0011-capability-extension-host.md) 中升级授权继承的判断范围，其余运行时、能力及市场信任决策继续生效。
- 相关：[安装规则](../extensions.md#安装与体验)、[安全边界](../security.md#能力最小化)

## 问题与选择

安装入口在每次升级时都重新请求确认，原生已存在的继承逻辑又只按主 / 次版本及权限不扩大判断。前者重复打断没有新授权决定的更新，后者无法准确表示用户要求的“权限变化才确认”：新增尚未授予的可选权限也是声明变化，而主版本变化本身不表示获得额外能力。

采用“免确认升级”：仍由用户点击触发，只有来源可信且一致、版本更高、必需权限 / 可选权限 / 网络来源与方法集合完全相同，才继承原启用状态和授权。顺序变化不影响判断，禁用与拒绝的可选能力保持原状；来源或声明变化、首次安装与普通本地文件导入继续审阅。当前条件集中于原生安装提交边界，前端预判只用于选择交互流程。

每次确认使操作频繁却没有新的决策依据；仅在前端跳过弹窗并补出新的同意对象，会混淆“保留授权”与“重新授权”。现有安装命令因此允许缺省确认，但原生在写锁内把它解释为严格的授权继承请求，不满足条件即拒绝。内置来源由宿主内嵌的完整包确认，市场保留验签及仓库 / 公钥身份检查，不接受前端来源标签作为信任依据。

## 契约、失败与验证

沿用当前命令和生成绑定，确认参数改为可空，不新增安装服务或持久化格式。包、安装身份、revision CAS、预编译后复核、前一版本回退及服务撤回保持原边界；冲突、验证或编译失败保留原安装，不自动重新确认或重放。授权变化、网络集合变化、市场换钥 / 换仓库、本地伪装内置、乱序声明、跨主次版本、禁用状态和并发冲突均须回归。安装详情的短文案不替代原生校验，UI 回归另覆盖真实滚动位置和有效焦点。

如果未来引入后台自动更新、运行时动态授权或新的信任来源，应重新审视触发与授权继承边界；不能直接将本次用户点击的免确认流程扩展为后台安装许可。
