# 2. 特性分支 rebase + `--no-ff` 合并

- 状态：已采纳
- 日期：2026-10-19
- 决策者：项目发起人
- 相关：[Git 协作规范](../conventions/git-workflow.md)

## 背景

团队要求"遵循 GitFlow"且"合并分支需要 rebase"。这两条在字面上有冲突：
GitFlow 的经典做法是用 `--no-ff` 合并出特性边界，而 rebase 追求线性历史。
需要明确一条不产生歧义的规则，否则每个人会按自己的理解执行。

## 备选方案

| 方案                                    | 优点                                                           | 缺点                                                       |
| --------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------- |
| **A. 分支内 rebase + 合并用 `--no-ff`** | 分支历史线性可读；develop 上每个特性有明确合并点，便于整块回滚 | 需要每个人理解 rebase，强推需谨慎                          |
| B. rebase + fast-forward                | 完全线性，历史最干净                                           | 丢失"这是一个特性"的边界，回滚要逐个 revert                |
| C. squash merge                         | 一个 PR 一个提交，develop 极干净                               | 丢失原子提交，`git bisect` 粒度变粗；大 PR review 压力集中 |
| D. 直接 merge develop 进特性分支        | 操作最简单                                                     | 特性历史混入他人提交，review 噪音大                        |

## 决策

采用 **方案 A**：

- 特性分支内部一律 `git rebase origin/develop`，禁止 `git merge develop`
- 合并动作用 `git merge --no-ff`，保留合并节点
- 只有自己的、未合并的特性分支允许 `--force-with-lease`

## 后果

**正面**

- 打开一个 PR，看到的是干净的线性提交，review 效率高
- `develop` 上每个特性一个合并节点，出问题可整块 revert
- 原子提交保留，`git bisect` 能定位到具体改动
- 尽早在 rebase 阶段处理与目标分支的冲突；目标分支继续推进时仍需重新检查

**负面**

- rebase 需要理解历史改写语义，操作失误时通过 `git reflog` 定位原提交并恢复
- 强推需要团队纪律，禁止 `--force`
- 提交数比 squash 方案多，需要靠合并节点分组阅读

**缓解措施**

- 将同步、冲突处理与恢复命令纳入协作规范，使操作可复核
- PR 模板里带「已 rebase 到最新 develop」复选框，reviewer 合并前确认
- 保护分支使用 `git pull --ff-only`，自己的特性分支才允许 rebase

## 复查条件

- 团队规模超过 15 人、提交频率极高，线性历史维护成本变高
- 出现多次因 rebase 误操作导致的事故
- 引入自动化发布流水线后，需要更简单的提交结构
