# 架构决策记录（ADR）

## 记录范围

一份 ADR 记录一个需要长期保留理由的技术决策，说明当时的问题、选择依据和代价。当前契约与操作方法由[文档索引](../README.md)中的指南维护。

## 记录门槛

需要后续维护者理解并延续技术取舍时再写，常见情况包括：

- 选择或替换会影响长期维护的核心依赖。
- 改变跨层契约、数据归属或分发方式，留下需要延续的约束。
- 为明确的成本或风险放弃更简单的方案，需要保留原因和代价。

普通功能、样式调整和缺陷修复在 PR 说明即可；跨模块改动本身不要求 ADR。方案分析与评审按 [设计门槛](../engineering-at-scale.md#设计评审与-adr-门槛) 选择适合的载体，ADR 只保留已采纳的长期取舍。

决策实施时更新对应架构或操作指南，并从中链接 ADR；无需在多处复制完整背景、方案和验证清单。

## 命名与状态

```text
docs/adr/0001-kebab-case-title.md
```

编号四位递增，不复用。状态只有四种：

| 状态           | 含义                               |
| -------------- | ---------------------------------- |
| `提议中`       | 还没定，正在讨论                   |
| `已采纳`       | 当前生效                           |
| `已废弃`       | 不再适用，但没有替代方案           |
| `被 000N 取代` | 有新决策覆盖了它，**不要删旧文件** |

ADR 采纳后保留原始决策与上下文。结论改变时新增 ADR 并标记取代关系；错别字、失效链接和不改变结论的事实澄清可以修订，通过 Git 保留修改记录。

局部取代时，在新旧记录页首注明覆盖范围与相互链接，其余决策继续生效。记录中的版本、预算、实施顺序和验收要求属于当时背景，不自动成为每次修改都要执行的流程。

## 模板

```markdown
# N. 标题（一句话说清做了什么决定）

- 状态：提议中 | 已采纳 | 已废弃 | 被 000N 取代
- 日期：YYYY-MM-DD
- 相关：[架构说明](../architecture.md)

## 背景与取舍

面临的问题、实际约束和有竞争力的备选方案。

## 决策

选了什么，一句话说清。

## 影响与复查

记录会影响维护的收益、代价；有明确复查条件时一并写出。
```
