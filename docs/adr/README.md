# 架构决策记录（ADR）

## 这是什么

一份 ADR 记录**一个重要的技术决策**：当时有哪些备选、为什么选了这个、代价是什么。
它不是会议纪要，也不是设计文档——它只回答一个问题：**半年后有人问"为什么不用 X"，能在这里找到答案。**

## 什么时候写

满足任一条件就写：

- 引入或替换核心依赖（框架、数据库、状态管理、构建工具）
- 改变跨层约定（IPC 形态、路由方案、目录分层）
- 做出"明知道有代价还是这么选"的取舍
- 否决了一个看起来更简单的方案

不用写：普通功能开发、样式调整、修 bug。

## 命名与状态

```
docs/adr/0001-kebab-case-title.md
```

编号四位递增，不复用。状态只有四种：

| 状态           | 含义                               |
| -------------- | ---------------------------------- |
| `提议中`       | 还没定，正在讨论                   |
| `已采纳`       | 当前生效                           |
| `已废弃`       | 不再适用，但没有替代方案           |
| `被 000N 取代` | 有新决策覆盖了它，**不要删旧文件** |

ADR 一旦采纳就**不再修改正文**。要改结论，写一份新的，把旧的标为"被取代"。
改历史等于毁掉决策的可追溯性。

## 模板

```markdown
# N. 标题（动宾结构，一句话说清做了什么决定）

- 状态：提议中 | 已采纳 | 已废弃 | 被 000N 取代
- 日期：YYYY-MM-DD
- 决策者：@某人 @某人
- 相关：[架构说明](../architecture.md)

## 背景

面临什么问题，有哪些约束（时间、人力、已有技术栈、合规要求）。

## 备选方案

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |

## 决策

选了什么，一句话说清。

## 后果

**正面**：得到了什么。

**负面**：付出了什么代价，以及打算怎么缓解。

## 复查条件

什么情况下应该重新评估这个决策（比如"团队规模超过 10 人"、"需要支持 Linux"）。
```
