# 架构决策记录（ADR）

## 记录范围

一份 ADR 记录一个影响长期演进的技术决策，包括背景、备选方案、选择依据、代价与复查条件，使后续变更能够追溯当时的约束。

## 记录门槛

满足任一条件就写：

- 引入或替换核心依赖（框架、数据库、状态管理、构建工具）
- 改变跨层约定（IPC 形态、路由方案、目录分层）
- 在已知成本或限制下作出长期技术取舍
- 否决了一个看起来更简单的方案

普通功能、样式调整和缺陷修复无需单独编写 ADR，除非同时改变长期技术决策。

涉及多个模块、兼容性、性能或发布恢复的变更，先按 [设计门槛](../engineering-at-scale.md#设计评审与-adr-门槛) 在 issue / PR 中说明方案和验收。提案讨论实现方案，ADR 只保留已采纳的长期取舍；决策实施时同步 [架构说明](../architecture.md) 和对应操作文档，不能只留一份 ADR 让当前说明过时。

## 命名与状态

```
docs/adr/0001-kebab-case-title.md
```

编号四位递增，不复用。状态只有四种：

| 状态           | 含义                               |
| -------------- | ---------------------------------- |
| `提议中`       | 还没定，正在讨论                   |
| `已采纳`       | 当前生效                           |
| `已废弃`       | 不再适用，但没有替代方案           |
| `被 000N 取代` | 有新决策覆盖了它，**不要删旧文件** |

ADR 采纳后保留原始决策与上下文。结论改变时新增 ADR 并标记取代关系；错别字、失效链接和不改变结论的事实澄清可以修订，通过 Git 保留修改记录。

## 模板

```markdown
# N. 标题（动宾结构，一句话说清做了什么决定）

- 状态：提议中 | 已采纳 | 已废弃 | 被 000N 取代
- 日期：YYYY-MM-DD
- 决策者：@某人 @某人
- 相关：[架构说明](../architecture.md)

## 背景

面临什么问题，有哪些约束（时间、人力、已有技术栈、合规要求）。

## 备选方案

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |

## 决策

选了什么，一句话说清。

## 后果

**正面**：得到了什么。

**负面**：付出了什么代价，以及打算怎么缓解。

## 复查条件

什么情况下应该重新评估这个决策（比如"团队规模超过 10 人"、"需要支持 Linux"）。
```
