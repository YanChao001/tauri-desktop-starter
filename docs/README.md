**没有 CHANGELOG。** 变更记录就是 git 历史本身：提交信息遵循 Conventional Commits，
版本边界由 tag 标记。查某个版本改了什么：

```bash
git log v1.1.0..v1.2.0 --oneline          # 两个版本之间
git log v1.2.0..HEAD --oneline --no-merges # 上个版本之后
git tag -l --sort=-v:refname | head -5     # 最近的版本
```

维护一份手写的变更日志，长期结果一定是「忘了更新」或「和 git 历史对不上」。
真要对外发版说明，发布时用上面第一条命令生成，再人工润色。

## 维护规则

### 一份事实只写一处

同一条规则、同一个数字、同一段命令，整个仓库里**只允许有一个定义点**，其他地方一律用链接指向它。

这条规则不是洁癖。真实踩过的坑：PR 的 diff 上限一度同时写在 `git-workflow.md`、`CONTRIBUTING.md`
和 PR 模板里，三份内容很快就对不上了。现在只在 `git-workflow.md` 定义，另两处指向它。

写文档前先 grep 一遍关键词，确认没有第二份。发现重复时，合并到信息最全的那份，其余改成一句链接。

### 不抄代码已经表达的东西

- 函数签名、参数类型、默认值——代码里有，文档不要复制一遍。文档只写"为什么这样设计"。
- 配置项的具体数值不粘贴，指向配置文件本身。
- 目录树可以列承担关键职责的文件，但新增普通文件不必回头改它；不要把它当成完整清单。

### 新增文档前先问一句

**能不能并进现有文档的一节？** 能并就别新建。

文档数量本身不是资产。13 份文档里如果有人只看其中 3 份，剩下 10 份就是在稀释注意力。
宁可让一份文档长一点、结构清楚一点，也不要拆成五份互相引用。

### 其他

- **文档和代码在同一个 PR 里改。** 接口变了文档不改，比没有文档更糟。
- 每份文档开头写清"这份文档解决什么问题"，不写正确的废话。
- 长文档用二级标题分节即可，不必每份都加目录；分节标题要能独立看懂。
- 失效的文档直接删，不要留着标注"已过时"——没人会去读第二遍。
- 变更记录不手写，用 git 历史代替（见上文）。
