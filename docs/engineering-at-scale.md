# 规模化开发指南

本文规定多业务模块、多人维护时的依赖方向、责任与设计门槛。当前实现见 [架构说明](./architecture.md)，操作和检查见 [文档索引](./README.md)。

## 能力范围与扩展条件

模板已有分层、类型化 IPC、迁移恢复、测试、签名发布入口和 ADR，可作为产品起点；CI 配置及演示页面不能代替目标设备、真实业务与运行保障的验收。

| 范围       | 产品扩大后需要落实                                   |
| ---------- | ---------------------------------------------------- |
| 业务与模块 | 业务不变量、账户权限、数据生命周期、公开契约与负责人 |
| 兼容与质量 | 真实升级路径、历史数据恢复、正式安装包验收与性能预算 |
| 协作       | 管理员配置分支保护，团队落实适用评审与影响分析       |
| 运行       | 支持责任、故障响应、恢复演练与发布后观察             |

当前没有远程账户认证、云同步、遥测上传、服务端监控或分阶段放量系统。本地会话、协作者和系统通知仅按演示 / 本机能力理解。现有 [Wasm 扩展与市场](./extensions.md) 的授权和验签不能替代新远程服务或第三方内容的信任边界设计。

## 文档层级与维护职责

| 层级               | 权威位置                                                                                                    | 维护时机                                             |
| ------------------ | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 产品目标和验收     | 产品 issue 或需求单                                                                                         | 功能进入实现前，写明用户、场景、范围和可验收结果     |
| 当前系统结构       | [architecture.md](./architecture.md) 与已形成独立边界的模块说明                                             | 模块职责、依赖方向、数据归属或运行行为变化时         |
| 设计提案与实施计划 | issue / PR，使用 [设计提案模板](./design-template.md)；需随代码维护的跨里程碑计划放 `docs/plans/`           | 出现设计门槛时先确定边界与验收；按已完成行为更新范围 |
| 决策理由           | [ADR](./adr/README.md)                                                                                      | 确定长期技术取舍时，记录被放弃方案和复查条件         |
| 实施和验收         | [开发](./development.md)、[测试](./testing.md)、[发布](./build-release.md)、[安全](./security.md)及对应规范 | 实际命令、检查和交付行为变化时                       |
| 某次变更和故障     | PR、Release、issue                                                                                          | 保留验证证据与处理结果，不复制成另一份长期规范       |

提案描述计划，架构记录现状，ADR 保留决策理由。落地后同步架构和操作指南并链接 ADR，不将未实现设计写成现有能力。普通功能在 PR 交代方案与验收，无须另建提案文件。

跨里程碑计划需要离线评审、并行执行或随代码长期维护时，可以在 `docs/plans/` 保留一份具名计划并补文档索引；明确拟议与已实现范围、模块归属、依赖、验收及恢复，PR 引用它，不再复制完整方案。计划不是逐日流水账，不保存每次命令输出、提交清单或代替权威指南；任务完成后收敛交付状态，当前契约转入所属指南。示例见 [设备工作台基座实施计划](./plans/device-workbench-foundation.md)。通用文档规则见 [维护规则](./README.md#维护规则)。

## 业务模块与依赖方向

当一组业务规则、页面和数据需要一起变化，且能独立定义边界和验收时，再引入 `src/features/<domain>/`。单页演示或纯展示组件继续放在现有目录；不按团队人数、文件数量或预想业务预建模块。

已有领域目录和职责见 [模块职责](./architecture.md#模块职责)。模型、校验、组件和测试就近维护；`public.ts` 等公开入口按实际调用需要创建，不急切聚合页面或提前上移状态。路由继续在 `routes.tsx` 维护懒加载。

依赖遵循这些规则：

- 外壳和路由可以组合领域公开能力；领域不依赖应用布局和路由注册实现。
- 领域可以依赖通用 UI、无业务含义的共享工具和原生门面；共享模块不反向导入领域。
- 跨领域访问只经过有明确语义的公开契约，不导入对方内部组件、状态或存储实现。跨领域用例由明确的上层入口编排；出现循环依赖时先调整责任归属，不用事件总线隐藏循环。
- 共享组件不拥有业务数据，领域不读取其他领域的数据库表或擅自改写其缓存。写入只由数据所属领域执行。
- Rust 命令调用服务，`lib.rs` 只组装；命令归属、绑定与错误规则见 [Rust 约定](./conventions/code-style.md#rust)，不为单个函数预建 trait 或仓库层。
- 前端通过 `src/lib/tauri.ts` 访问原生能力；内部可按领域拆分，保持入口、生成绑定和结构化错误边界。

当前领域依赖主要靠评审，原生导入边界已有 ESLint 检查。出现实际违规时再补充依赖检查并接入 CI，不能将尚未启用的规则称为自动强制。

## 模块负责人和变更影响

团队建立后，为外壳与 UI、设置与 IPC、原生数据与桌面能力、构建发布指定负责人和替补，一人可负责多个范围。负责人协调契约与评审，不限制其他人修改代码。

在领域已有说明、issue 或团队说明中只维护一份责任表，记录代码范围、负责人及替补、公开入口、数据归属、允许依赖、关键验收和故障入口。需要自动指定评审人时再配置 `CODEOWNERS`；模板未预设生效的领域所有者。

每个跨模块 PR 在影响面中说明调用方、事件订阅方、数据版本、权限、设置、目标平台和发布路径的变化。负责人只评审与改动相关的范围；涉及数据、安全或发布契约时，邀请对应维护者，不要求所有人审查每个 PR。

## 设计评审与 ADR 门槛

满足任一项时，在大规模实现前使用 [设计提案模板](./design-template.md) 完成影响分析：

- 新业务域、跨域依赖或共享状态的归属发生变化。
- IPC、事件、导入导出格式、数据库或设置 schema 存在兼容性影响。
- 新增远程服务、凭据、权限、第三方内容或可执行扩展。
- 改变启动流程、后台任务并发模型或窗口生命周期策略，或引入明显影响性能、包体及分发的新依赖。
- 改变签名、更新通道、数据恢复方式或需要协调多步发布。

随代码维护的跨里程碑计划可以承载同一份设计影响分析，按 [文档层级](#文档层级与维护职责) 在 PR 中引用，不要求再复制一份提案。

提案给出范围、可比较方案、失败路径、兼容与恢复方案、可验证的验收条件；由受影响模块负责人确认，按仓库已配置的评审规则合并。单维护者保留自审和验证证据，不能虚构第二位审批人。紧急故障可以先按 hotfix 恢复，但后续应补齐影响说明和缺失的回归。

需要长期保留的技术取舍按 [ADR 记录门槛](./adr/README.md#记录门槛) 记录。一份提案可链接多个 ADR；小改动无需为完成流程单独编写 ADR。设计通过不等于验证通过，合并时仍需记录实际结果和未验证的平台。

评审按 [约束与复杂度](./conventions/code-style.md#约束与复杂度) 和 [测试的收益与边界](./testing.md#测试的收益与边界) 判断新增协调、校验、兼容分支与门禁是否必要，不提高普通局部改动的流程门槛。

## 契约与数据演进

以下版本含义不同，不能互相代替：

| 标识                                | 作用                              | 兼容策略                                                                                   |
| ----------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------ |
| 应用版本                            | 安装、发布和自动更新              | [版本规则与回滚](./build-release.md#版本号四个地方必须一致)                                |
| 设置 schema                         | 偏好文档格式                      | 旧格式迁移、未来版本拒写；规则归 [设置模型](../src/lib/settings-model.ts)                  |
| SQLite `user_version`               | 本地数据库结构                    | 事务迁移、未来版本拒写；实现归 [database.rs](../src-tauri/src/database.rs)                 |
| 笔记备份 `format` / `schemaVersion` | 跨进程、跨安装版本保存的逻辑 JSON | 严格验证支持的格式和 schema；恢复前保留完整安全备份，事务失败回滚                          |
| 设置 revision / 笔记 version        | 并发写入冲突检测                  | 它们是数据修订号，不是 schema 版本                                                         |
| IPC / 事件契约                      | 前端和 Rust 的调用、错误、通知    | 当前前后端随同一安装包发布；生成绑定约束源码一致，不提供运行时输入校验或独立客户端版本协商 |

IPC 随同安装包发布，无需预加网络协议版本；任务历史用于查询与显式重试，重启不自动续跑。出现独立客户端、持久队列或远程同步时，再设计协议版本、能力协商与支持期限。

跨边界契约至少定义：输入范围与大小、结果和稳定错误码、超时及取消、并发冲突、重试是否安全、事件顺序与失效语义。创建、批量保存或导出等可能产生副作用的操作不能无条件自动重试；真实业务应先设计幂等键、事务或结果查询。取消前端等待不等于原生操作已回滚。

版本支持范围遵循 [开发阶段的兼容取舍](./conventions/code-style.md#约束与复杂度)，不默认要求所有开发快照可互相升级。每次数据变更说明当前格式、明确支持的来源及失败恢复方式；不支持的旧格式明确拒绝并保留原件。确有存量数据迁移承诺时，再定义支持窗口、迁移步骤、旧结构移除和恢复方案，并用对应历史样本及损坏 / 中断场景验收，见 [数据与恢复验证](./testing.md#数据与恢复验证)。

现有备份与启动隔离恢复的范围见 [数据存储](./architecture.md#数据存储) 和 [恢复、诊断与更新](./architecture.md#恢复诊断与更新)。派生产品仍须按自己的数据量、历史版本与存储故障验收，不能推断已有云端恢复、自动保留策略或生产演练证据。

后台任务与窗口协商属于共享契约：维护有界队列、执行位置、合作取消、终态与历史；worker 退出前不释放执行位置，前端停止等待不撤销落盘结果。未保存工作提供实际保存 / 放弃动作，支持协商取消并保留离页回调。通知避免多窗重复发送，关闭确认覆盖全部参与窗口。

## 性能、发布与故障反馈

性能预算按目标设备、平台和产品需求确定，并放在对应需求或设计提案里。至少覆盖冷 / 热启动到可交互、重复启动恢复、关键列表 / 搜索、长任务对 UI 的影响，以及需要长期运行场景的内存 / CPU。记录数字目标、测量口径、基线和结果；没有实测时写“未测”，不要从演示页面、debug 构建或固定延迟推导正式性能。

启动的采样和正式安装版验收以 [安装版与启动验收](./testing.md#安装版与启动验收) 为准。预算建立后，修改相关路径的 PR 提供同环境前后对比；超过预算或出现白屏、重复进程、数据损坏时，先解决阻断项再发版。当前 CI 没有通用性能阈值门禁。

发布证据、支持责任与观察按 [发布检查清单](./build-release.md#发布检查清单) 和 [发布后观察](./build-release.md#发布后观察) 留存。需要分阶段放量时，先设计通道与发布控制。

故障通过 issue 跟踪；涉及安全和敏感数据的记录放私密渠道。影响启动、白屏、重复实例、数据丢失或升级的故障，保留版本 / 哈希、平台、复现条件、影响范围、脱敏日志、定位结论、恢复动作及回归验证。复盘补充哪些检测和评审没有发现问题，将整改分配给负责人并给出验收条件；有明确期限再写期限。修复进入代码、测试或操作指南后关闭对应行动项，不另建无人维护的事故文档目录。
