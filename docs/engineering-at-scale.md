# 规模化开发指南

本文面向从模板演进为多业务模块、多人维护产品的团队。它规定何时补充模块边界、设计评审和运行保障；当前运行实现以 [架构说明](./architecture.md) 为准，操作与检查分别由开发、测试、发布文档维护。

## 能力范围与扩展条件

现有文档已经覆盖桌面基座的开发闭环：分层与 IPC 边界、代码和界面约定、单元及真实桌面测试、签名发布、安全政策和 ADR。它可以作为大项目的起点；仅凭目录完整和规范数量，不能认定已具备大型产品的全部工程能力。

| 维度 | 当前事实                                                        | 产品扩大后需要落实                                                                           |
| ---- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 模块 | 前端按页面、组件、Provider、门面组织，Rust 按存储和桌面能力划分 | 按实际业务域建立公开入口、负责人和跨域契约，控制依赖方向                                     |
| 业务 | 展厅和交互页是本地演示，SQLite 笔记是持久化示例                 | 为真实业务定义不变量、权限、数据生命周期与验收条件                                           |
| 变更 | PR 模板、ADR、CI 配置已在仓库中                                 | 仓库管理员配置保护和评审要求，团队落实领域评审、设计与影响分析                               |
| 兼容 | IPC 绑定生成；设置和数据库有迁移、未来版本保护及并发冲突处理    | 根据真实升级路径验证迁移、备份恢复和导入导出兼容                                             |
| 质量 | 有三端 CI 和真实桌面 E2E 配置                                   | 用正式安装包验收目标设备、建立性能预算和发布证据，不能用 CI 配置代替实测                     |
| 运行 | 有本地日志、诊断页、更新与恢复入口                              | 落实支持责任人、故障响应、恢复演练和发布后观察；当前没有遥测上传、服务端监控或分阶段放量系统 |

引入账户、远程同步、插件、第三方网页或凭据时，需要针对新增信任边界做设计。当前模板没有实现这些系统，不应把演示协作者、通知或资料收藏当成账户和服务能力。

## 文档层级与维护职责

| 层级           | 权威位置                                                                                                    | 维护时机                                         |
| -------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 产品目标和验收 | 产品 issue 或需求单                                                                                         | 功能进入实现前，写明用户、场景、范围和可验收结果 |
| 当前系统结构   | [architecture.md](./architecture.md) 与已形成独立边界的模块说明                                             | 模块职责、依赖方向、数据归属或运行行为变化时     |
| 设计提案       | issue / PR，使用 [设计提案模板](./design-template.md)                                                       | 出现下文设计门槛时，先评审再实现                 |
| 决策理由       | [ADR](./adr/README.md)                                                                                      | 确定长期技术取舍时，记录被放弃方案和复查条件     |
| 实施和验收     | [开发](./development.md)、[测试](./testing.md)、[发布](./build-release.md)、[安全](./security.md)及对应规范 | 实际命令、检查和交付行为变化时                   |
| 某次变更和故障 | PR、Release、issue                                                                                          | 保留验证证据与处理结果，不复制成另一份长期规范   |

提案讨论“准备怎么改”，架构文档说明“现在怎样运行”，ADR 说明“为何决定这样做”。提案合并后更新当前架构和操作指南，链接采纳的 ADR；不把未实现设计写成现有能力。普通功能直接在 PR 交代方案和验收，无须另建提案文件。

## 业务模块与依赖方向

当一组业务规则、页面和数据需要一起变化，且能独立定义边界和验收时，再引入 `src/features/<domain>/`。单页演示或纯展示组件继续放在现有目录；不按团队人数、文件数量或预想业务预建模块。

以下是领域形成后的组织示例，当前仓库尚未建立这一目录：

```text
src/features/notes/
  public.ts         对外导出的能力和类型
  pages/            该领域的路由页面，保持按需加载
  components/       只服务于该领域的组件
  model.ts          领域状态、不变量与纯逻辑
  *.test.ts(x)      规则与行为测试，和实现放在一起
```

只创建实际需要的文件。`public.ts` 是边界示例，不要求通过一个聚合入口急切导入所有页面；路由继续保留懒加载。特性内部的状态、校验和组件就近维护，不因“可能复用”上移到全局目录。

依赖遵循这些规则：

- 外壳和路由可以组合领域公开能力；领域不依赖应用布局和路由注册实现。
- 领域可以依赖通用 UI、无业务含义的共享工具和原生门面；共享模块不反向导入领域。
- 跨领域访问只经过有明确语义的公开契约，不导入对方内部组件、状态或存储实现。跨领域用例由明确的上层入口编排；出现循环依赖时先调整责任归属，不用事件总线隐藏循环。
- 共享组件不拥有业务数据，领域不读取其他领域的数据库表或擅自改写其缓存。写入只由数据所属领域执行。
- Rust 继续由命令边界调用服务，服务维护业务规则，存储适配系统 API 或数据库。某个领域形成独立职责后再拆成模块；不让 `lib.rs` 承担业务，也不为单个函数建立 trait 和仓库层。
- 前端仍通过 `src/lib/tauri.ts` 访问原生能力。门面过大时可内部按领域拆分并保留清晰入口，不绕过生成绑定和结构化错误。

这些是评审约定，当前没有自动检查所有领域依赖的架构规则。多个领域落地后，可在真实违规出现的位置补充 ESLint 导入限制或依赖检查，并在 CI 执行；配置启用前不能称其已被自动强制。

## 模块负责人和变更影响

模板没有预设真实维护者。维护者应在仓库团队建立后，为应用外壳与 UI、设置与 IPC、原生数据与桌面能力、构建发布分别指定负责人和替补。一个人可以负责多个范围；负责人负责契约和评审协调，不代表代码只能由其修改。

领域形成时，在该领域已有说明中记录责任与边界；尚无独立模块时在 issue 或仓库团队说明中维护一份对应表。至少包含：代码范围、负责人和替补、公开入口、拥有的数据、允许依赖、关键验收及运行故障入口。不要同时维护多份人员名单。需要自动指定评审人时，再将真实 GitHub 用户或团队映射进 `CODEOWNERS`；当前仓库没有预置生效的领域所有者规则。

每个跨模块 PR 在影响面中说明调用方、事件订阅方、数据版本、权限、设置、目标平台和发布路径的变化。负责人只评审与改动相关的范围；涉及数据、安全或发布契约时，邀请对应维护者，不要求所有人审查每个 PR。

## 设计评审与 ADR 门槛

满足任一项时，在大规模实现前使用 [设计提案模板](./design-template.md) 完成影响分析：

- 新业务域、跨域依赖或共享状态的归属发生变化。
- IPC、事件、导入导出格式、数据库或设置 schema 存在兼容性影响。
- 新增远程服务、凭据、权限、第三方内容或可执行扩展。
- 改变启动流程、后台任务并发模型或窗口生命周期策略，或引入明显影响性能、包体及分发的新依赖。
- 改变签名、更新通道、数据恢复方式或需要协调多步发布。

提案给出范围、可比较方案、失败路径、兼容与恢复方案、可验证的验收条件；由受影响模块负责人确认，按仓库已配置的评审规则合并。单维护者保留自审和验证证据，不能虚构第二位审批人。紧急故障可以先按 hotfix 恢复，但后续应补齐影响说明和缺失的回归。

需要长期保留的技术取舍按 [ADR 记录门槛](./adr/README.md#记录门槛) 记录。一份提案可链接多个 ADR；小改动无需为完成流程单独编写 ADR。设计通过不等于验证通过，合并时仍需记录实际结果和未验证的平台。

## 契约与数据演进

以下版本含义不同，不能互相代替：

| 标识                         | 作用                           | 兼容策略                                                                                   |
| ---------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------ |
| 应用版本                     | 安装、发布和自动更新           | [版本规则与回滚](./build-release.md#版本号四个地方必须一致)                                |
| 设置 schema                  | 偏好文档格式                   | 旧格式迁移、未来版本拒写；规则归 [设置模型](../src/lib/settings-model.ts)                  |
| SQLite `user_version`        | 本地数据库结构                 | 事务迁移、未来版本拒写；实现归 [database.rs](../src-tauri/src/database.rs)                 |
| 设置 revision / 笔记 version | 并发写入冲突检测               | 它们是数据修订号，不是 schema 版本                                                         |
| IPC / 事件契约               | 前端和 Rust 的调用、错误、通知 | 当前前后端随同一安装包发布；生成绑定约束源码一致，不提供运行时输入校验或独立客户端版本协商 |

当前 IPC 不需要为了形式增加网络协议版本。出现独立更新的外部客户端、持久队列、导入文件或远程同步后，再设计相应协议版本、能力协商和支持期限。

跨边界契约至少定义：输入范围与大小、结果和稳定错误码、超时及取消、并发冲突、重试是否安全、事件顺序与失效语义。创建、批量保存或导出等可能产生副作用的操作不能无条件自动重试；真实业务应先设计幂等键、事务或结果查询。取消前端等待不等于原生操作已回滚。

每次数据变更说明哪些历史版本可升级、哪些旧版本不能读新数据、失败后如何恢复。迁移先增加兼容结构，再迁移和验证，最后按实际支持窗口移除旧结构；不要把删除旧字段和恢复方案留到发布后考虑。验收用脱敏历史样本和损坏 / 中断场景，规则见 [数据与恢复验证](./testing.md#数据与恢复验证)。

当前模板没有产品级备份导出与恢复界面，也没有云端恢复服务。未来版本保护能防止误写，不能替代备份；产品有持久业务数据时，要在首次对外承诺可靠性前落实并验证恢复路径。

## 性能、发布与故障反馈

性能预算按目标设备、平台和产品需求确定，并放在对应需求或设计提案里。至少覆盖冷 / 热启动到可交互、重复启动恢复、关键列表 / 搜索、长任务对 UI 的影响，以及需要长期运行场景的内存 / CPU。记录数字目标、测量口径、基线和结果；没有实测时写“未测”，不要从演示页面、debug 构建或固定延迟推导正式性能。

启动的采样和正式安装版验收以 [安装版与启动验收](./testing.md#安装版与启动验收) 为准。预算建立后，修改相关路径的 PR 提供同环境前后对比；超过预算或出现白屏、重复进程、数据损坏时，先解决阻断项再发版。当前 CI 没有通用性能阈值门禁。

发布负责人在 Release 或发布 issue 留下目标平台、产物哈希、安装升级结果、未验证范围、恢复演练结果和支持入口；执行规则见 [发布检查清单](./build-release.md#发布检查清单)及 [发布后观察](./build-release.md#发布后观察)。当前静态更新源没有自动分阶段放量能力，需要时先设计通道与发布控制。

故障通过 issue 跟踪；涉及安全和敏感数据的记录放私密渠道。影响启动、白屏、重复实例、数据丢失或升级的故障，保留版本 / 哈希、平台、复现条件、影响范围、脱敏日志、定位结论、恢复动作及回归验证。复盘补充哪些检测和评审没有发现问题，将整改分配给负责人并给出验收条件；有明确期限再写期限。修复进入代码、测试或操作指南后关闭对应行动项，不另建无人维护的事故文档目录。
