# 规模化开发指南

本文用于处理跨模块、存量数据、权限和发布等实质取舍。日常改动沿 [贡献流程](../CONTRIBUTING.md) 实现并验证；当前结构见 [架构说明](./architecture.md)。

## 能力范围与扩展条件

模板提供可操作的桌面示例、类型化 IPC、持久化与恢复、受控扩展和分发链路。派生产品按真实业务和部署环境补充能力；演示、CI 配置和本机检查分别说明自己的覆盖范围。

远程账户、云同步、遥测或独立后台等能力在出现实际需求时设计。现有 [扩展授权](./extensions.md) 只覆盖其声明的信任边界，新增服务按其数据和权限重新分析。

## 文档层级与维护职责

文档职责以 [维护规则](./README.md#一份事实只写一处) 为准。通常在 issue / PR 中说明问题、方案和验收，落地时更新受影响的当前指南；长期取舍按 [ADR 门槛](./adr/README.md#记录门槛) 留存原因。

需要跨会话、离线评审或并行执行时，再在 `docs/plans/` 保存一份具名计划并补索引。计划说明范围、依赖和可验收结果；当前契约落入指南，单次检查结果留在 PR。已有计划能够承载方案时直接引用，不额外复制提案。

## 业务模块与依赖方向

当一组业务规则、页面和数据需要一起变化，且能独立定义边界和验收时，再引入 `src/features/<domain>/`。单页演示或纯展示组件继续放在现有目录；不按团队人数、文件数量或预想业务预建模块。

已有领域目录和职责见 [模块职责](./architecture.md#模块职责)。模型、校验、组件和测试就近维护；`public.ts` 等公开入口按实际调用需要创建，不急切聚合页面或提前上移状态。路由继续在 `routes.tsx` 维护懒加载。

依赖遵循这些规则：

- 外壳和路由可以组合领域公开能力；领域不依赖应用布局和路由注册实现。
- 领域可以依赖通用 UI、无业务含义的共享工具和原生门面；共享模块不反向导入领域。
- 跨领域访问只经过有明确语义的公开契约，不导入对方内部组件、状态或存储实现。跨领域用例由明确的上层入口编排；出现循环依赖时先调整责任归属，不用事件总线隐藏循环。
- 共享组件不拥有业务数据，领域不读取其他领域的数据库表或擅自改写其缓存。写入只由数据所属领域执行。
- Rust 命令调用服务，`lib.rs` 只组装；命令归属、绑定与错误规则见 [Rust 约定](./conventions/code-style.md#rust)，不为单个函数预建 trait 或仓库层。
- 前端通过 `src/lib/tauri.ts` 访问原生能力；内部可按领域拆分，保持入口、生成绑定和结构化错误边界。

当前领域依赖主要靠评审，原生导入边界已有 ESLint 检查。出现实际违规时再补充依赖检查并接入 CI，不能将尚未启用的规则称为自动强制。

## 模块负责人和变更影响

多人持续维护同一领域时，在已有模块说明或团队约定中记录负责人和公开入口；需要自动分配评审时再配置 `CODEOWNERS`。单维护者使用同一份设计与验证记录，无需预建角色、替补和责任表。

跨模块 PR 只说明实际变化的调用方、数据、权限、生命周期或分发路径，邀请受影响的维护者评审。团队规模和模块数量本身不增加提案或测试要求。

## 设计评审与 ADR 门槛

下列变化在实现前需要明确影响、取舍和验收，通常直接写在 issue / PR；方案较复杂时使用 [设计提案模板](./design-template.md) 的相关章节：

- 跨域依赖或共享状态的归属发生变化，需要协调调用方。
- IPC、事件、导入导出格式、数据库或设置 schema 存在兼容性影响。
- 新增远程服务、凭据、权限、第三方内容或可执行扩展。
- 改变启动、后台并发或窗口生命周期策略，或引入明显影响性能、包体及分发的新依赖。
- 改变签名、更新通道、数据恢复方式或需要协调多步发布。

影响分析给出问题、改动范围、实质替代方案和可验证结果；仅在涉及存量数据、分发或外部副作用时补充相应恢复安排。按仓库已有评审规则合并，设计分析本身不新增审批角色。紧急故障先恢复，再补齐影响说明和必要回归。

调整已有实现、内部函数或局部展示且没有上述影响时，直接在 PR 交代行为与检查即可。是否增加抽象、兼容分支或验证，按 [约束与复杂度](./conventions/code-style.md#约束与复杂度) 和 [测试收益](./testing.md#测试的收益与边界) 判断。

## 契约与数据演进

以下版本含义不同，不能互相代替：

| 标识                                | 作用                              | 兼容策略                                                                                   |
| ----------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------ |
| 应用版本                            | 安装、发布和自动更新              | [版本规则与回滚](./build-release.md#版本号四个地方必须一致)                                |
| 设置 schema                         | 偏好文档格式                      | 旧格式迁移、未来版本拒写；规则归 [设置模型](../src/lib/settings-model.ts)                  |
| SQLite `user_version`               | 本地数据库结构                    | 事务迁移、未来版本拒写；实现归 [database.rs](../src-tauri/src/database.rs)                 |
| 笔记备份 `format` / `schemaVersion` | 跨进程、跨安装版本保存的逻辑 JSON | 严格验证支持的格式和 schema；恢复前保留完整安全备份，事务失败回滚                          |
| 设置 revision / 笔记 version        | 并发写入冲突检测                  | 它们是数据修订号，不是 schema 版本                                                         |
| IPC / 事件契约                      | 前端和 Rust 的调用、错误、通知    | 当前前后端随同一安装包发布；生成绑定约束源码一致，不提供运行时输入校验或独立客户端版本协商 |

IPC 随同安装包发布，无需预加网络协议版本；任务历史用于查询与显式重试，重启不自动续跑。出现独立客户端、持久队列或远程同步时，再设计协议版本、能力协商与支持期限。

契约说明调用者正确使用所需的知识：不可信输入的范围、可操作的错误，以及实际存在的并发、取消或事件顺序。涉及副作用时明确重试是否安全；只有需要自动重试或重复提交时，再选择幂等键、事务或结果查询。取消等待不表示原生操作已回滚。

版本支持范围遵循 [开发阶段的兼容取舍](./conventions/code-style.md#约束与复杂度)。数据格式变化说明实际支持的来源及失败后的数据状态；有存量迁移承诺时，再定义支持窗口、迁移步骤和恢复方式，并按 [数据与恢复验证](./testing.md#数据与恢复验证) 选择对应样本。未知 / 未来格式仍保留原件并拒绝误写。

备份、恢复、后台任务与窗口协商的当前契约见 [架构说明](./architecture.md)，扩展租约见 [扩展生命周期](./extensions.md#执行存储与生命周期)。修改这些规则时更新所属定义和受影响调用方。

## 性能、发布与故障反馈

出现性能目标、回归或高频路径改动时，选择受影响的启动、交互、任务或长期运行场景，记录目标设备、测量口径及同环境基线。按实际产品需求设置预算，避免为每次改动建立全平台性能矩阵；演示和 debug 数据只说明相应环境。

启动的采样和正式安装版验收以 [安装版与启动验收](./testing.md#安装版与启动验收) 为准。预算建立后，修改相关路径的 PR 提供同环境前后对比；超过预算或出现白屏、重复进程、数据损坏时，先解决阻断项再发版。当前 CI 没有通用性能阈值门禁。

发布证据、支持责任与观察按 [发布检查清单](./build-release.md#发布检查清单) 和 [发布后观察](./build-release.md#发布后观察) 留存。需要分阶段放量时，先设计通道与发布控制。

故障通过 issue 留存复现条件、影响、定位和恢复结果，敏感信息走私密渠道。影响数据或分发的故障补充版本与平台证据；只有发现可重复的流程缺口时，再增加检查或调整规范。整改以代码、回归或操作指南为交付，记录放在原 issue / PR。
