# 代码风格与命名规范

本文维护命名、组件与复杂度取舍。格式和静态规则交给现有工具，评审关注行为与边界；检查选择见 [测试规范](../testing.md#日常验证范围)。

## 总原则

沿用相同职责的已有写法，以可读的控制流程表达意图；外部数据在边界运行时校验，模块内部沿用类型与不变量。注释解释原因和契约，不复述命名与类型。

## 文件与目录命名

| 对象                 | 规则                                  | 示例                                   |
| -------------------- | ------------------------------------- | -------------------------------------- |
| 目录                 | `kebab-case`                          | `src/components/settings-panel/`       |
| React 组件文件       | `kebab-case`                          | `app-shell.tsx`、`language-switch.tsx` |
| React 组件名         | `PascalCase`                          | `AppShell`、`LanguageSwitch`           |
| Hook 文件            | `use-*.ts`；包含 JSX 时用 `.tsx`      | `use-native-resource.ts`               |
| Hook 函数            | `useXxx`                              | `useWindowState`                       |
| 普通工具模块         | `kebab-case`                          | `format-date.ts`                       |
| Node 工程脚本        | `kebab-case.mjs`，使用 ES 模块        | `scripts/clean.mjs`                    |
| 类型定义             | 就近定义；共享契约可集中在 `types.ts` | `commands/types.ts`                    |
| Rust 文件 / 模块     | `snake_case`                          | `window_state.rs`                      |
| 常量（模块级真常量） | `UPPER_SNAKE_CASE`                    | `MAX_RETRY_COUNT`                      |

布尔变量使用清晰的判断语义，如 `isVisible`、`hasChanges`、`canSubmit`、`shouldRetry`；沿用外部 API 和持久化字段名时不强制改名。
事件处理器：组件内部 `handleXxx`，作为 prop 传出去时叫 `onXxx`。

面向开发者的工程命令通过 `package.json` 提供入口，平台专用能力由 Node 脚本按需调用系统工具。

工程脚本的终端输出（帮助、进度、结果与错误）统一使用英文，与 Node、Vite、Cargo 和 Tauri 工具链保持一致；工程文档与源码注释仍按仓库的中文约定维护。

## 组件约定

组件按来源和职责遵循以下约定：

| 位置                       | 来源            | 规则                                                          |
| -------------------------- | --------------- | ------------------------------------------------------------- |
| `src/components/ui/`       | shadcn CLI 生成 | 可以改样式；维持调用方兼容，升级前审查 CLI 差异并保留本地定制 |
| `src/components/<domain>/` | 项目维护        | 命名导出，一个文件一个主组件                                  |
| `src/features/<domain>/`   | 项目维护        | 已形成边界的领域模型 / 组件，测试就近；不预建空层             |
| `src/pages/`               | 项目维护        | 默认导出，一个文件对应一条路由                                |

- 组件难以独立理解、测试或复用时拆分；行数只作提示，不为满足数字拆出空壳。
- Props 类型命名为 `XxxProps`，就近定义；组件直接写函数并标注 props 类型。
- 组件文件名与组件名对应，`app-shell.tsx` → `export function AppShell`。
- `ui/` 沿用上游格式，不批量格式化；其 ESLint / Prettier 例外见 `.prettierignore`、`eslint.config.js`。`src/styles/shadcn.css` 逐字保留上游内容，不手改。
- 测试与被测职责就近维护；上游 UI 组件的自有行为回归放在 `src/components/` 的同名测试文件中，以接受 lint 与格式检查。

## TypeScript

- **手写业务代码禁止 `any`。** 未知类型用 `unknown`，在使用处收窄；`lib/generated/` 保留导出工具的运行时代码，不手改生成的断言。
- 对象类型优先用 `type`，需要声明合并时用 `interface`。
- 原生门面、共享协议等公共边界显式标注返回类型；组件、Hook 与内部工具可以使用可靠的类型推断，不为形式重复复杂类型。
- 不用 `enum`，用 `as const` 对象 + 联合类型：

```ts
export const THEMES = ["light", "dark", "system"] as const;
export type Theme = (typeof THEMES)[number];
```

- 非空断言 `!` 用于已有不变量保证存在的值；其他缺失情况显式处理。
- Rust DTO 与命令从 `bindings.rs` 生成 TypeScript，页面通过 `lib/tauri.ts` 调用；生成类型不替代边界运行时校验，变更步骤见 [Rust](#rust)。
- 领域规则和纯类型从所属模型导入，Provider 负责状态和生命周期；表单 schema、查询缓存与表格状态留在实际所属领域。局部演示依赖按页面加载，持久偏好复用现有设置来源。
- 有快照的异步订阅先监听再读取，按 revision / 请求代次过滤旧结果；卸载后拦截回调并释放晚到的取消函数。未保存工作使用 `useUnsavedWork`，保存 / 放弃响应协商的 AbortSignal。相关生命周期见 [架构说明](../architecture.md)。

手写应用源码的 Tauri 静态与动态导入限制由 `eslint.config.js` 检查；门面、生成绑定及测试文件是配置中的例外。测试组件时优先 mock `@/lib/tauri`，验证门面与底层插件契约时再直接 mock `@tauri-apps/*`，不要为了测试绕过应用代码的边界。

本应用使用客户端渲染，环境分支对应实际支持的浏览器 / WebView；测试需要 DOM 时使用 jsdom 或测试替身。校验和兼容的取舍见下文。

## 重复与抽象

抽象集中维护同一规则与变化边界；以实际用途衡量它能否减少同步修改和理解成本。

### 约束与复杂度

实现和评审以当前需求、信任边界与独立失败场景决定复杂度；测试的取舍见 [测试规范](../testing.md#测试的收益与边界)。

- **维护当前契约。** 接口、协议或模型变化时同步更新受影响的调用方和文档。版本兼容须有明确支持对象与验收场景；原始数据保留、未知 / 未来格式拒写和失败恢复继续遵循现有数据保护契约。
- **校验放在信任边界。** 外部输入、IPC、存储读取与副作用提交点按风险校验；同一信任域内使用已建立的类型与不变量。再次校验对应新的不可信输入或并发变化，保留原生权限复核和版本冲突检查。
- **限制对应实际资源。** 路径规则用于路径，展示名称与 JSON 成员键按各自语义处理；配额和格式限制应保护具体资源或协议。合法写入的数据应能完整保存、备份和恢复；单项损坏按所属集合的契约隔离。
- **状态与抽象有实际用途。** 状态由一处持有，其他层使用派生值或单向适配；参数、模式和扩展点服务当前调用方或明确支持承诺，随需求移除失效分支。
- **协调覆盖需要互斥的资源。** 锁和队列按身份、资源与提交阶段划分，独立快照的序列化和磁盘同步放在数据锁外；全局退出等操作保留必要屏障。
- **按实际成本优化。** 拖动、输入等高频交互区分预览和最终提交，消除确定的重复持久化、复制与扫描；缓存、批处理和调度层用于已有性能需要。

### 按职责与变化原因抽象

同一规则、协议或安全边界共用定义；相似展示按用途和变化原因决定是否组合。提取后的职责应能独立描述。

### 什么算重复

需要同步变化的校验、计算、状态与常量属于同一规则。三五行表达式、相同样式类及变化原因独立的 JSX 可以分开；合并后持续增加模式分支时，重新评估职责。

### 抽到哪

| 重复的东西        | 放哪                              |
| ----------------- | --------------------------------- |
| 纯逻辑、格式化    | `lib/`                            |
| 带状态的 UI 逻辑  | `hooks/`                          |
| 展示结构          | `components/`                     |
| 跨进程的调用      | `lib/tauri.ts`                    |
| Rust 侧的公共逻辑 | `src-tauri/src/` 下的独立职责模块 |

### 不要做的抽象

先把代码放在实际所属模块；多个独立用途组合职责明确的组件。仅有一个局部用途时保持直接实现，出现共同规则再提取。

## Rust

- 命令函数统一返回 `NativeResult<T>`，使用 `NativeError { code, message, retryable }`；可恢复的运行时错误不用 `unwrap()` / `expect()`。启动失败和测试断言可以明确终止。错误码表达稳定语义，前端不解析字符串。
- 命令函数名用动词开头：`read_config`、`save_settings`、`export_report`。
- 基础命令放 `commands.rs`，领域命令放 `*_commands.rs` 或已有生命周期 / 恢复模块；服务维护规则，`lib.rs` 负责组装。命令与 DTO 在 `bindings.rs` 注册，变更后运行 `pnpm bindings:generate`、`pnpm bindings:check` 并提交生成结果；前端由门面消费生成契约。完整步骤见 [新增页面到 IPC 与测试](../demo-modules.md#新增页面到-ipc-与测试)。
- 新增或改变错误码时，同步核对 `src/lib/native-error.ts` 的本地化映射与两份语言词典；未知错误可用通用兜底，但不能让已有可恢复错误丢失可操作的提示。
- 文件、网络、数据库操作使用异步 API；同步阻塞调用通过现有 `blocking::run` / `spawn_blocking` 移出异步工作线程。
- 内部日志记录必要上下文并脱敏；返回前端的错误按用户可采取的动作组织，避免暴露敏感路径、令牌或请求内容。
- 格式、Clippy 和 Rust 测试的执行范围见 [Rust 测试](../testing.md#rust-测试)，CI 按工作流执行检查。

## 导入顺序

保持现有文件的导入顺序；新模块可按以下分组组织。当前未安装导入排序插件，不为了排序产生无关 diff：

```ts
// 1. Node 内置
import path from "node:path";

// 2. 第三方
import { useState } from "react";

// 3. 项目别名
import { Button } from "@/components/ui/button";

// 4. 当前模块内的相对路径
import { localHelper } from "./local-helper";
```

项目内跨目录导入优先使用 `@/`，模块内部使用相对路径。

## 注释

注释说明设计原因、契约边界和反直觉行为，避免逐行复述代码。

### 注释层级

| 位置     | 何时需要                                                     | 写什么                                                   |
| -------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| 文件头   | `lib/tauri.ts`、`commands.rs`、`routes.tsx` 等入口或边界文件 | 职责与允许的依赖边界；普通页面、组件不写模板化文件头     |
| 导出 API | 签名不足以说明契约时                                         | 生命周期、失败条件或调用约束，不重复参数类型             |
| 局部代码 | 存在反直觉行为、兼容处理或需要解释的决策时                   | 原因与限制；大量逐行解释时先改进命名、控制流程或模块边界 |

### 格式

- TS/TSX 的公共契约使用 `/** */`，局部解释使用 `//`；Rust 公共契约使用 `///`，模块说明使用 `//!`。
- 局部解释放在对应代码附近，沿用文件格式。
- 自有代码、测试与工程配置的解释性注释统一使用中文；短句可省略句末标点，多句使用完整标点。
- 保留 API 名、技术标识、命令、路径和工具要求的指令注释。`src/components/ui/`、`src/styles/shadcn.css` 等上游原样资源与 `src/lib/generated/` 等生成文件保留其来源格式，不为语言统一手工修改；其他自有文件中的外部摘录应注明来源。

### 不要写

- 复述代码的注释：`// 把 pending 设为 true`。
- 被注释掉的代码——git 里有历史，不需要现场留档。
- 作者签名、修改日期、`@author`：`git blame` 比这准确。
- 大段装饰性分隔线（`// ===== 工具函数 =====`）；按职责组织代码，难以独立理解时再拆分。

### 待办

待办说明具体缺口，尽量关联可追踪的 issue；确有期限时注明负责人和期限：

```ts
// TODO(#123): 等待上游支持取消后，移除本地取消适配
```

## 文案与排版

界面说明、反馈位置与长文布局遵循 [说明与布局稳定](./ui-guidelines.md#说明与布局稳定)。

- 界面文案通过 `src/i18n/zh-CN.ts` 与 `en.ts` 维护，两份入口分别组合基础和功能词典；新键同时补齐中英，新语言在 `registry.ts` 注册。技术名词保留原词（WebView、IPC、Rust）。
- 中英文之间加空格：`打开 WebView 设置`，不是 `打开WebView设置`。
- 中文标点用全角，代码与命令用半角。
- 按钮文案用动词开头：「保存」「新建项目」，不用「确定」这种无信息量的词（除非是系统约定的确认框）。
- 错误提示说清「发生了什么 + 该怎么办」，不要只抛一句「操作失败」。
